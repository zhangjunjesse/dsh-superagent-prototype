# Jarvis Gateway 开发前方案评审

日期：2026-11-13。对象：[开发前方案](jarvis-gateway-design.md)。最终版本：D2；状态：两路独立静态评审及修订后的定点复审完成。第 1–5 节保留开发前评审，第 6 节起记录后续获准实施后的审查，不混用两阶段证据。

本次评审是静态架构／范围／恢复机制审查，不是实现验收。未运行业务测试、未安装依赖、未启动或改动服务。评审依据包含项目约束、现有调用路径和源码证据；子任务统一使用 GPT-6.1 Sol / max。

## 过程记录

- 成稿前分别核查投递边界及会话反馈／环境依据，未将依据收集冒充正式评审。
- D1 完成后提交两路独立评审：一路审路由、约束与授权；另一路审持久反馈、会话生命周期、范围和恢复。
- D1 共发现 4 项 P1 阻断、5 项 P2 建议，无 P0。先修订为 D2，再定点复审，未把“已经写进方案”直接当成评审通过。
- 路由复审又发现普通 Trigger 与受限 Trigger 混批的遗漏，补齐后再确认关闭。两路复审均明确本范围无剩余阻断，可以在后续实施授权后进入 P0 受控接口与环境验证。

## 1. 最终结论

**D2 在本次静态设计评审范围内通过，可作为 P0 验证和后续分阶段实施的依据。** 这不等于可以立即打开真实任务写入口；P0／P1 的能力与原子性验证完成前，不进入真实业务联调。

设计采用：同包 Gateway、独立命令 Thread、持久定向约束、领域事务消费回执、Gateway 收件箱与独立表达状态机。superagent 保留任务生命周期及执行权威，Jarvis 保留唯一用户入口。

两个明确边界必须随方案交付：

- G2 约束有 command／trigger 来源的协议副作用，不声称已经隔离主 Session 所有无来源管理工具的内容；note／retry 等旧能力不能作为 Gateway 命令的成功回执。若要扩为全面能力隔离，需要另外的可信调用归因设计。
- 反馈保证已提交的 Jarvis Outbox 消息和当前可行动状态，不宣称完整重放所有短暂状态变化。跨来源自动接管与镜像不在首期。

## 3. 实施仍需取得的证据

1. **运行环境**：完整底座的构建产物、依赖、宿主版本兼容与执行平台。当前 Windows Jarvis-only 4318 环境不能作为底座已可运行的证明；Linux／WSL 是否可复用仍需核查，不自动迁移原实例。
2. **领域原子性**：用真实 Engine／持久 Store 验证接收前无 fanout、消费前无错投、所有订阅入口和普通混批入口受约束，终局消费回执与副作用同事务；保持旧来源合法多订阅行为。
3. **会话恢复**：目标 DSH 的插件来源、followup、inbox 恢复、单输入与 turn／assistant 关联及 flush；不能使用 inject 或人类 prompt 冒充可靠通知表达。
4. **故障窗口**：依 T10／T11／T14／T17 验证提交未知、消息取消、生成失败、投影断点、清空切换和无普通 reply 的终局通知。若宿主能力不足或需更大底座变更，携证据返回设计评审，不降低标准。
5. **产品语义**：首期仅操作 Gateway 创建并绑定的工作；一用户轮次最多一个有副作用操作；清空上下文保持原工作关联并承接未表达事件。这些是首期设计取舍，进入真实交付时需一并核对，不冒充既有功能。
