# 组织启动进度与等待优化

2026-11-22，本次只修改隔离工作树，未发布、重启或修改 4318 服务。

## 已实现的行为

- 点击启动或重启后，立即显示“已请求启动，等待确认”及实际等待时间。`control.action` 的模型/工具/技能预检仍按原机制执行；收到新一次启动的真实记录前，不把上一代的“已就绪”当成本次结果。
- POST 等待期间每 500 毫秒读取现有只读 topology 接口。仅更新运行状态投影，保留已读取的配置，不打开管理 owner、不等待完整设置查询。页面隐藏时不发请求；迟到的轮询不能覆盖 POST 的最终结果。
- 原 Setup 和 Runtime 在 GitHub 检查、其他来源检查、写入并验证执行环境、原生会话初始化、最终准备完成处发出阶段回执。进程建立由原管理器计时；最终就绪还等待原生命周期参与方恢复完成。
- 管理器通过现有私有 IPC 核对进程和代次。新增记录只接收固定阶段和状态，保存时间及耗时，不记录命令、参数、环境值、路径、账号或原始错误文本。
- 继续使用原真实就绪、设置受阻、初始化失败和停止清理机制。设置未通过只显示“等待设置”，不写 ready 事件；停止期间先显示“正在取消启动”，仅清理完成后记录取消。原有初始化等待、委派停止和清理重试规则保持，未增加强杀或跳过等待的取消路径。
- 有界阶段投影持久保存在原 `processes.json` 的可选 `startup` 字段，过程与结果追加到原 `lifecycle.jsonl`。管理器重新取得独占锁后，可恢复上次记录；尚未结束的启动或取消标为 interrupted，保留最后持久观测的耗时并另记发现时间，不把离线时间计入工作，不自动重放任务。旧记录继续可读。

## 为什么修改原项目的这些位置

已核实的链路是 `ProcessManager -> child.mjs -> OriginalProcess -> Runtime.initialize -> Setup.resolve -> resolveDeployment`。原 Runtime 同时拥有仓库与账号校验、执行环境写入/验证、原生会话初始化及后台循环的真实边界。仅在 Jarvis 外层增加计时无法分开这些等待，也不能判断原设置校验是否受阻。因此在原有流程中增加可选、无业务副作用的观察回调，没有复制或替换原机制。

上一轮本机样本从 start 到 ready 为 23.924 秒；首个执行环境文件生成前约 23.22 秒。该样本来自已有生命周期记录与当时产物时间，只是定位依据，未把可变 mtime 用作回归断言。阅读原代码后确认，已连接 GitHub 的身份与仓库权限两次独立 REST 读在 `resolveDeployment` 串行执行，所以等待优化也必须落在此原校验入口。

现在两次读并行执行，查询与现有 CLI/环境保持；等待两者 settled 后，仍按身份错误、身份格式、仓库读取、仓库格式、push 权限的旧顺序解释。仓库改名采用 canonical name、缺账号、不可读、只读及未知权限仍逐项拒绝；没有缓存或略过验证。可选飞书检查失败仍沿原规则记录健康问题而不阻塞其他来源。

管理器原启动方法是既有生命周期热点；本次不搬迁其所有权或清理逻辑。阶段验证、时间计算与恢复投影放在 `startup-progress.mjs`，同一份规则用于运行快照和恢复，避免把新状态混进业务状态机。
